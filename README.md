# ระบบแจ้งเตือนนักศึกษาผ่าน LINE

ระบบส่งข้อความแจ้งเตือนนักศึกษาผ่าน LINE Official Account
สร้างจากแบบ `Line Notify System.dc.html` ใน Claude Design

- **Frontend** — Vite + React + TypeScript (SPA)
- **Backend** — Express + PostgreSQL พร้อมพร็อกซีสำหรับ LINE Messaging API
- **ฐานข้อมูล** — PostgreSQL (`pg`) รหัสผ่านเข้ารหัสด้วย bcrypt

## เริ่มใช้งาน

### 1. ติดตั้ง dependencies

```bash
npm install
```

### 2. สร้างฐานข้อมูล

```bash
createdb line_notify
```

ถ้าไม่มีคำสั่ง `createdb` ใน PATH ให้ใช้ psql แทน:

```bash
psql -U postgres -c "CREATE DATABASE line_notify"
```

บน Windows ที่ติดตั้งจาก installer มาตรฐาน psql จะอยู่ที่
`C:\Program Files\PostgreSQL\17\bin\psql.exe`

### 3. ตั้งค่าการเชื่อมต่อ

คัดลอก `.env.example` เป็น `.env` แล้วใส่รหัสผ่าน PostgreSQL ของคุณ:

```
DATABASE_URL=postgresql://postgres:รหัสผ่านของคุณ@localhost:5432/line_notify
```

### 4. สร้างตารางและใส่ข้อมูลตัวอย่าง

```bash
npm run db:setup
```

### 5. รันระบบ

```bash
npm run dev
```

- หน้าเว็บ: http://localhost:5173
- API: http://localhost:8787

เข้าสู่ระบบด้วยบัญชีทดสอบ — ชื่อผู้ใช้งาน `admin` รหัสผ่าน `admin`

## โครงสร้างฐานข้อมูล

| ตาราง | เก็บอะไร |
| --- | --- |
| `users` | ผู้ใช้งานระบบ รหัสผ่านเก็บเป็น bcrypt hash เท่านั้น |
| `majors` | สาขาวิชาและคณะ ชื่อสาขาห้ามซ้ำ |
| `students` | ข้อมูลนักศึกษา อ้างอิงสาขาด้วย `major_id` |
| `student_groups` | การจัดกลุ่ม อ้างอิง `students.student_id` ด้วย foreign key |
| `history_log` | ประวัติการส่ง เก็บเวลาเป็น `timestamptz` |
| `app_settings` | ค่าตั้งค่าแบบ key/value |

ข้อกำหนดที่บังคับความถูกต้องของข้อมูล:

- ลบสาขาวิชา → นักศึกษาไม่หาย แต่ `major_id` กลายเป็น `NULL` (`ON DELETE SET NULL`)
- ลบนักศึกษา → การจัดกลุ่มของคนนั้นถูกลบตาม (`ON DELETE CASCADE`)
- เปลี่ยนรหัสนักศึกษา → การจัดกลุ่มอัปเดตตาม (`ON UPDATE CASCADE`)
- นักศึกษาหนึ่งคนอยู่ในกลุ่มเดียวกันซ้ำไม่ได้
- จัดกลุ่มด้วยรหัสที่ไม่มีในระบบไม่ได้ — จะขึ้นข้อความให้เพิ่มข้อมูลนักศึกษาก่อน
- จำนวนนักศึกษาต่อสาขาคำนวณจากตาราง `students` ตอน query ไม่ได้เก็บไว้ จึงไม่มีทางไม่ตรง

## API

| Endpoint | ทำอะไร |
| --- | --- |
| `GET /api/health` | สถานะเซิร์ฟเวอร์ ฐานข้อมูล และโหมด LINE |
| `GET /api/bootstrap` | โหลดข้อมูลทั้งหมดในคำขอเดียว (หน้าเว็บใช้ตอนเปิด) |
| `POST /api/auth/login` | ตรวจสอบรหัสผ่านกับ bcrypt hash แล้วสร้าง session |
| `GET /api/auth/me` | ถามว่าใครล็อกอินอยู่ (หน้าเว็บใช้ตอนเปิด) |
| `POST /api/auth/logout` | ทำลาย session ฝั่งเซิร์ฟเวอร์ |
| `GET/POST/PATCH/DELETE /api/users` | จัดการผู้ใช้งาน |
| `GET/POST/PATCH/DELETE /api/majors` | จัดการสาขาวิชา |
| `GET/POST/PATCH/DELETE /api/students` | จัดการนักศึกษา |
| `POST /api/students/bulk` | นำเข้าหลายรายการจาก CSV |
| `GET/POST/PATCH/DELETE /api/student-groups` | จัดการการจัดกลุ่ม |
| `GET/POST/PATCH/DELETE /api/history` | จัดการประวัติการส่ง |
| `POST /api/line/verify` | ทดสอบ token กับ LINE |
| `POST /api/line/connect` | เชื่อมนักศึกษาเข้ากับ LINE OA (ตรวจสอบ uid จริงก่อนบันทึก) |
| `POST /api/line/disconnect` | ยกเลิกการเชื่อมต่อของนักศึกษา |
| `POST /api/line/messages/send` | ส่งข้อความถึงทั้งกลุ่มด้วย multicast (ใช้โดยหน้าส่งข้อความ) |
| `POST /api/line/push` | ส่งข้อความรายบุคคล (ใช้ภายใน) |

### การส่งข้อความถึงทั้งกลุ่ม

หน้า "ส่งข้อความ" เรียก `POST /api/line/messages/send` โดยส่งไปแค่**ชื่อกลุ่ม**
ไม่ได้ส่งรายชื่อผู้รับ เซิร์ฟเวอร์เป็นฝ่ายทำทั้งหมด:

1. ดึง uid ของนักศึกษาทุกคนในกลุ่มจากฐานข้อมูล
2. ข้ามคนที่ยังไม่มี uid แล้วรายงานจำนวนกลับมา
3. ตัด uid ที่ซ้ำกันออก (LINE ไม่รับผู้รับซ้ำใน request เดียว)
4. แบ่งเป็นชุดละไม่เกิน **500 คน** ตามข้อจำกัดของ LINE
5. ส่งด้วย **`POST /v2/bot/message/multicast`** พร้อม `X-Line-Retry-Key`
   เพื่อไม่ให้ข้อความซ้ำถ้าต้องส่งใหม่
6. บันทึกลง `history_log` ทั้งกรณีสำเร็จและล้มเหลว

ข้อดีเทียบกับเดิมที่ยิง push ทีละคน — กลุ่ม 400 คนใช้ **1 request** แทน 400 request
และจำนวนผู้รับที่บันทึกไว้ตรงกับคนที่เซิร์ฟเวอร์ส่งถึงจริง เพราะเบราว์เซอร์ไม่ได้เป็นคนนับ

### การเชื่อมต่อนักศึกษากับ LINE OA

ปุ่ม **เชื่อมต่อ LINE OA** ในหน้า "จัดกลุ่มนักศึกษา" ทำงานตามลำดับนี้:

1. ตรวจรูปแบบ uid (`U` + ตัวอักษร/ตัวเลข 32 ตัว)
2. ตรวจว่ามีนักศึกษารหัสนี้ในระบบ
3. ตรวจว่า uid ยังไม่ถูกใช้กับนักศึกษาคนอื่น
4. **เรียก `GET /v2/bot/profile/{uid}` ของ LINE** — จุดนี้คือหัวใจ
   เพราะ LINE จะคืนโปรไฟล์ก็ต่อเมื่อผู้ใช้เพิ่ม Official Account เป็นเพื่อนแล้วเท่านั้น
   ถ้าได้ 404 แปลว่านักศึกษายังไม่ได้เพิ่มเพื่อน หรือ uid ผิด
5. บันทึกชื่อบัญชี รูปโปรไฟล์ และเวลาที่เชื่อมต่อลงฐานข้อมูล
6. ส่งข้อความต้อนรับให้อัตโนมัติ

`line_connected_at` ที่ไม่เป็น `NULL` จึงหมายถึง "LINE ยืนยันแล้วว่าติดต่อได้จริง"
ต่างจาก `line_uid` ที่เป็นเพียงข้อความที่มีคนพิมพ์ใส่ไว้

ถ้าแก้ไข uid ของนักศึกษาในภายหลัง ระบบจะล้างสถานะการเชื่อมต่อทันที
เพราะโปรไฟล์เดิมเป็นของบัญชีคนละอันแล้ว ต้องกดเชื่อมต่อใหม่เพื่อยืนยัน

## การตรวจสอบสิทธิ์

ทุก endpoint ภายใต้ `/api` ต้องมี session ยกเว้น `/api/auth/login` กับ `/api/health`
ตัวกรองถูกใส่ไว้ที่ระดับ `/api` ทั้งก้อน **endpoint ที่เขียนเพิ่มในอนาคตจึงถูกปิดโดยอัตโนมัติ** ไม่ต้องกลัวลืมใส่

| สิ่งที่ทำ | ใครทำได้ |
| --- | --- |
| อ่านข้อมูลนักศึกษา สาขา กลุ่ม ประวัติ | ทุกคนที่ล็อกอิน |
| เพิ่ม/แก้ นักศึกษา สาขา กลุ่ม | ทุกคนที่ล็อกอิน |
| ส่งข้อความ · เชื่อมต่อ LINE OA | ทุกคนที่ล็อกอิน |
| **ลบข้อมูลทุกชนิด** | แอดมินเท่านั้น |
| **จัดการผู้ใช้งาน** | แอดมินเท่านั้น |
| **ทดสอบ Channel Access Token** | แอดมินเท่านั้น |

รายชื่อผู้ใช้งานไม่รั่วผ่าน `/api/bootstrap` ด้วย — ผู้ใช้ทั่วไปจะได้ `users: []`

**Session** เก็บในตาราง `session` ของ PostgreSQL ไม่ได้เก็บในหน่วยความจำ
รีสตาร์ทเซิร์ฟเวอร์แล้วไม่มีใครหลุดล็อกอิน คุกกี้เป็น `httpOnly` จึงอ่านจาก JavaScript ไม่ได้
และตั้ง `secure` อัตโนมัติเมื่อ `NODE_ENV=production`

**"จดจำการเข้าสู่ระบบ"** ติ๊ก = session อยู่ 30 วัน · ไม่ติ๊ก = หลุดเมื่อปิดเบราว์เซอร์

**Rate limit** ล็อกอินผิดเกิน 5 ครั้งใน 15 นาที จะถูกบล็อกตาม IP
ช่วงที่ถูกบล็อก **รหัสที่ถูกต้องก็เข้าไม่ได้** จนครบเวลา — ถ้าติดตอนพัฒนา รีสตาร์ทเซิร์ฟเวอร์เพื่อล้างตัวนับ

## การเชื่อมต่อ LINE

เบราว์เซอร์เรียก `api.line.me` โดยตรงไม่ได้ — LINE ไม่ส่ง CORS header กลับมา
คำขอทุกรายการจึงผ่านเซิร์ฟเวอร์ Express แทน ซึ่งช่วยให้ Channel Access Token
ไม่หลุดไปอยู่ในเบราว์เซอร์ด้วย

ใส่ token ใน `.env`:

```
LINE_CHANNEL_ACCESS_TOKEN=<token จาก LINE Developers Console>
```

**ถ้ายังไม่ได้ตั้งค่า token ระบบจะทำงานใน "โหมดจำลอง"** — การส่งจะสำเร็จแบบจำลอง
ไม่มีการส่งข้อความจริง และหน้าจอจะระบุไว้ชัดเจน ทำให้ทดลองใช้ระบบได้ครบทุกหน้าโดยไม่ต้องมี LINE OA

> token ถูกอ่านจาก `.env` ของเซิร์ฟเวอร์เท่านั้น ไม่รับจากเบราว์เซอร์
> หน้าตั้งค่าจึงไม่มีช่องให้กรอกหรืออ่าน token และระบบจะปฏิเสธ token ที่ถูกระบุว่ารั่วไหลแล้ว
> (ดู `server/compromised-tokens.js`)

## การ deploy

ระบบออกแบบให้รันเป็น **service เดียว**: Express เสิร์ฟทั้ง API และไฟล์จาก `dist/`
ที่ origin เดียวกัน ทำให้คุกกี้ session ทำงานได้โดยไม่ต้องตั้ง CORS

### ฐานข้อมูล

ใช้ PostgreSQL จากผู้ให้บริการที่มี free tier แบบ**ไม่หมดอายุ** แล้วนำ connection string
มาใส่ที่ `DATABASE_URL` พร้อมตั้ง `DATABASE_SSL=true`

> ไม่แนะนำ PostgreSQL ฟรีของ Render เพราะหมดอายุและถูกลบหลัง 30 วัน
> ซึ่งไม่เหมาะกับข้อมูลนักศึกษา

### ตัวแปรที่ต้องตั้งบน host

| ตัวแปร | ค่า |
| --- | --- |
| `NODE_ENV` | `production` |
| `TRUST_PROXY` | `true` (จำเป็นเมื่ออยู่หลัง proxy) |
| `DATABASE_URL` | connection string ของฐานข้อมูล |
| `DATABASE_SSL` | `true` |
| `SESSION_SECRET` | ค่าสุ่มยาว ๆ |
| `LINE_CHANNEL_ACCESS_TOKEN` | token ที่ issue ใหม่ |

ไม่ต้องตั้ง `API_PORT` — host กำหนด `PORT` ให้เอง และเซิร์ฟเวอร์จะใช้ค่านั้น

### ขั้นตอน

```bash
# 1. build frontend + สร้างตารางในฐานข้อมูล
npm run deploy:prepare
```

```bash
# 2. สร้างบัญชีแอดมินตัวจริง (ห้ามใช้ db:seed บน production)
ADMIN_PASSWORD=<รหัสผ่านยาวอย่างน้อย 12 ตัว> npm run db:create-admin -- --username <ชื่อผู้ใช้> --name "<ชื่อ-นามสกุล>"
```

```bash
# 3. สตาร์ท
npm start
```

บน Render มีไฟล์ `render.yaml` เป็น Blueprint ให้แล้ว (`buildCommand` และ
`healthCheckPath` ตั้งไว้เรียบร้อย) เหลือกรอก `DATABASE_URL` กับ token ใน Dashboard

### ⚠️ ก่อนเปิดให้คนภายนอกใช้

- **ห้ามรัน `npm run db:seed` บน production** เพราะสร้างบัญชี `admin/admin`
  ให้ใช้ `db:create-admin` แทน และลบหรือตั้งรหัสผ่านใหม่ให้บัญชี `admin`
- **issue Channel Access Token ใหม่** ตัวที่เคยฝังในไฟล์ดีไซน์ถูกบล็อกไว้แล้ว
  (ดู `server/compromised-tokens.js`)
- **เปิด backup ของฐานข้อมูล** ตอนนี้ไม่มีเลย ข้อมูลหายคือหายถาวร

### ข้อจำกัดที่ยังเหลือ

- **ตั้งเวลาส่งยังไม่ทำงาน** เลือกวันเวลาได้แต่ระบบส่งทันที ยังไม่มี scheduler
- **ตัวนับ rate limit อยู่ในหน่วยความจำ** ถ้ารันหลาย instance จะนับแยกกัน
  และนับตาม IP เท่านั้น เครือข่ายที่ออกเน็ตผ่าน NAT ร่วมกันจะล็อกกันเอง
- **ไม่มี log การล็อกอินที่ล้มเหลว** ตรวจย้อนหลังไม่ได้ว่ามีใครพยายามเจาะ

สิ่งที่ทำต่างจากต้นแบบโดยตั้งใจ:

- **ข้อมูลอยู่ใน PostgreSQL** — ต้นแบบเก็บทุกอย่างไว้ในหน่วยความจำของหน้าเว็บ
  ข้อมูลหายทุกครั้งที่รีเฟรช และใช้ร่วมกันหลายเครื่องไม่ได้
- **รหัสผ่านเข้ารหัสด้วย bcrypt** — ต้นแบบเก็บรหัสผ่านเป็นข้อความธรรมดาในโค้ด
  และตรวจสอบในเบราว์เซอร์ ตอนนี้ตรวจที่เซิร์ฟเวอร์และไม่เคยส่ง hash กลับมาที่หน้าเว็บ
- **ส่งข้อความผ่านเซิร์ฟเวอร์** — ต้นแบบเรียก `api.line.me` จากเบราว์เซอร์
  ซึ่งถูก CORS บล็อกเสมอ และบันทึกประวัติเป็น "ล้มเหลว" ทุกครั้ง
- **Channel Access Token อยู่ฝั่งเซิร์ฟเวอร์** — ต้นแบบเก็บ token จริงไว้ใน `localStorage`
- **ประวัติการส่งเก็บเวลาจริง** — ต้นแบบเก็บเป็นข้อความอย่าง `"11 ก.ค. 10:24"` ที่ไม่มีปี
  ทำให้ปฏิทินต้องเดาปีเอง ตอนนี้เก็บเป็น `timestamptz` และจัดรูปแบบตอนแสดงผล
- **นำเข้า CSV ได้จริง** — ต้นแบบเพียงปิดหน้าต่างโดยไม่อ่านไฟล์
- **ออกรายงานได้จริง** — ปุ่ม "ออกรายงาน (Excel)" สร้างไฟล์ CSV ที่มี UTF-8 BOM
  เปิดใน Excel แล้วภาษาไทยไม่เพี้ยน (ไม่ใช่ `.xlsx` จริง เพื่อลดการพึ่งพา library)
- **หน้าตั้งค่าและหน้าผู้รับเข้าถึงได้** — ทั้งสองหน้ามีอยู่ในต้นแบบแต่ไม่มีเมนูใดลิงก์ไปถึง
- **ผู้ใช้ที่สถานะ "ไม่ได้ใช้งาน" เข้าสู่ระบบไม่ได้** — ต้นแบบตรวจแค่ username กับ password
- **สถานะการเชื่อมต่อเป็นค่าจริง** — ต้นแบบแสดง "เชื่อมต่อ LINE สำเร็จ" ไว้ตายตัว

### ข้อจำกัดที่ยังเหลืออยู่

- **ยังไม่มี session** — หน้าเว็บจำสถานะเข้าสู่ระบบไว้ในหน่วยความจำเท่านั้น
  และ endpoint ของข้อมูลยังไม่ได้ตรวจสิทธิ์ ถ้าจะนำขึ้นใช้งานจริงต้องเพิ่ม
  session หรือ JWT แล้วบังคับตรวจสิทธิ์ในทุก endpoint ก่อน
- **ตัวเลขบนหน้าภาพรวมยังเป็นค่าคงที่** — จำนวน 312, 4,820, 98.4% มาจากแบบดีไซน์
  ยังไม่ได้คำนวณจากฐานข้อมูล (อยู่ใน `src/data/seed.ts`)
- **หน้าผู้รับมีกลุ่มตัวอย่างจากแบบดีไซน์ปนอยู่** — ส่วนที่ทำงานจริงคือกลุ่มด้านบน
  ที่มาจากตาราง `student_groups`
